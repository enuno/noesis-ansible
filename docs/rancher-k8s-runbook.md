# Rancher Manager deployment runbook (k3s + Tailscale operator ingress)

## Purpose and architecture

Deploys Rancher Manager onto the single-node k3s cluster with a private,
tailnet-only HTTPS endpoint. There is no public exposure of any kind: no
NodePort, no LoadBalancer, no public DNS, no Tailscale Funnel, and k3s's
Traefik/ServiceLB are disabled cluster-wide by policy.

Traffic path:

```
authorized tailnet client
  -> https://rancher.tailf99a0.ts.net          (MagicDNS, Let's Encrypt cert)
  -> tailscale operator proxy pod ts-rancher-* (TLS terminated here)
  -> ClusterIP Service rancher:80 (HTTP)
  -> rancher pod(s)                            (chart value tls=external)
```

- Chart: vendored `rancher-stable/rancher` 2.15.3 at
  `charts/vendor/rancher` (see "Kubernetes version deviation" below).
- Release: `rancher` in namespace `cattle-system`, `replicas: 1`.
- Single replica on a single-node cluster: this is NOT a highly available
  deployment. Do not raise replicas on this cluster.
- `tls=external` is the chart's supported external-TLS-termination mode:
  Rancher serves HTTP on :80, its probes switch to http :80 /healthz, and no
  cert-manager resources are rendered. cert-manager is deliberately NOT
  installed.
- The chart-managed Ingress is disabled (`ingress.enabled=false`); the role
  applies a dedicated `networking.k8s.io/v1` Ingress with
  `ingressClassName: tailscale`, short host `rancher`, backend
  `rancher:80`. The operator publishes
  `rancher.tailf99a0.ts.net` in the Ingress status, and the role asserts the
  published hostname equals Rancher's configured `hostname` value.
- The existing shared tailscale-operator (v1.104.1, ns `tailscale`) is
  reused as-is. This deployment must not install a second operator, rotate
  its OAuth credentials, or touch other services' `ts-*` proxy state.

## Kubernetes version deviation (read before operating)

Upstream rancher-stable 2.15.3 declares `kubeVersion: < 1.37.0-0`; this
cluster runs k3s `v1.37.1+k3s1`, and Helm hard-fails the constraint with no
override flag. Every published rancher-stable/rancher-latest chart at
2026-10-30 capped below 1.37, and the SUSE support matrix certifies Rancher
2.15.2 on k3s 1.34–1.36 only.

The vendored copy changes EXACTLY one line
(`kubeVersion: < 1.38.0-0`), verified by a full-tree diff against the
upstream tarball (sha256
`343888c66421a9f5666b562cdfeca751d63da994edbe7b1b36752f8ffcf5ecd4`;
see `charts/vendor/rancher/VENDORED.md`). **Rancher 2.15.3 on Kubernetes
v1.37 is an unsupported-by-upstream combination, approved by the operator
on 2026-10-30.** When upstream certifies 1.37, switch
`rancher_k8s_chart_ref` back to the official repo chart and remove the
vendored copy.

## Secrets

Bitwarden Secrets Manager is the durable credential authority.
Project: `72974d0e-81af-4678-bab7-b46000985859`.

| Record | Purpose | Lifecycle |
|---|---|---|
| `rancher_k3s_bootstrap_password` | Initial Rancher bootstrap password, generated by the role, escrowed BEFORE first cluster use | Reused verbatim on reruns; never regenerated or rotated by the playbook |
| `rancher_k3s_admin_password` | Permanent administrator password set during first-deploy initialization | Created only on first deploy; reruns only verify it still authenticates (401 = drift, hard failure — never silent rotation) |

Record ids are printed by `bws secret list <project> -o json`; values are
never logged (every secret-bearing task is `no_log: true`).

Runtime credential copies (unavoidable, documented — Bitwarden remains the
durable authority):

- Kubernetes Secret `bootstrap-secret` (ns `cattle-system`): the chart
  stores the bootstrap password and feeds it to the pod via env
  `CATTLE_BOOTSTRAP_PASSWORD`. After administrator initialization it is
  only a stale initial credential.
- Helm release metadata (`helm get values rancher -n cattle-system`): the
  rendered values include the bootstrap password. Access is bounded by the
  same cluster-admin boundary as the Secret itself.
- bws 2.1.0 `secret create` accepts the value only as a positional argument
  (no stdin/--value-file). The role passes it via the process environment,
  not the command string; residual exposure is a transient argv/environ
  entry on the single-tenant controller during the create call.

Managed runtime state, deliberately NOT escrowed: the operator-owned
`ts-rancher-*` state Secrets (Tailscale node identity) and the
operator-issued TLS private keys are managed by the Tailscale operator and
follow its lifecycle. Exporting them is not required for recovery and is
not authorized.

## Target and execution

Inventory: `inventory/rancher-k8s/hosts.ini` — group `rancher_k8s`, one
host (`noesis-lab`, the k3s control node, `ansible_user=ansible`, become
root), kubeconfig `/etc/rancher/k3s/k3s.yaml`, context `default`.
Durable site values live in `inventory/rancher-k8s/group_vars/all.yml`;
reruns use the same inventory so a future run cannot revert the release.

The repo `ansible.cfg` references a missing `.vault_pass`; this play has no
vault content on its path, so run with a minimal config (absolute
`roles_path` — relative entries resolve against the config file's
directory, not the cwd):

```bash
cd ~/projects/noesis-ansible
printf '[defaults]\nroles_path=%s/roles\n' "$PWD" > /tmp/nocfg.ini

# Static checks
ANSIBLE_CONFIG=/tmp/nocfg.ini ansible-playbook -i inventory/rancher-k8s/hosts.ini \
  playbooks/rancher-k8s.yml --syntax-check
/usr/bin/python3 tests/rancher_k8s/test_offline.py
helm lint charts/vendor/rancher

# Dry run (see "Check-mode limitations" — a preview, not proof)
ANSIBLE_CONFIG=/tmp/nocfg.ini ansible-playbook -i inventory/rancher-k8s/hosts.ini \
  playbooks/rancher-k8s.yml --check

# Deploy (controller env must carry BWS_ACCESS_TOKEN)
ANSIBLE_CONFIG=/tmp/nocfg.ini ansible-playbook -i inventory/rancher-k8s/hosts.ini \
  playbooks/rancher-k8s.yml

# Idempotency proof: same command again, expect changed=0
```

## Check-mode limitations

- No credential is generated and no Bitwarden record is written; with a
  missing bootstrap record the values render with a literal
  `CHECKMODE-PLACEHOLDER` password.
- Waits and health checks are skipped (their probes would be undefined).
- Helm diff output is approximate (server-side dry run).
- A green `--check` is a preview of intended changes, NOT evidence of a
  working deployment.

## Verification

The role itself waits for and asserts: release deployed, Deployment
available, populated Service endpoints, Ingress status hostname equal to
the configured FQDN, `ts-rancher-*` proxy pod Running+Ready, HTTPS 200 on
`/healthz` (certificate validated, no `-k`), and the UI document loading
on `/` with a Rancher marker. Manual spot checks:

```bash
kubectl -n cattle-system get deploy,pod,svc,endpoints,ingress
helm list -n cattle-system
curl -sS https://rancher.tailf99a0.ts.net/healthz   # expect 200 "ok"
```

Verification from the deployment host proves tailnet reachability for THIS
tailnet client only; for a stronger guarantee, repeat the curl from a
second tailnet device.

## Rollback and recovery

Rollback (task-owned resources only):

```bash
helm uninstall rancher -n cattle-system        # post-delete hook runs
kubectl delete ingress rancher -n cattle-system
# only if fully decommissioning:
kubectl delete namespace cattle-system
```

Never delete: the tailscale-operator release/secret, other services' `ts-*`
proxy pods or state Secrets, shared Tailscale CRDs, or pre-existing
Bitwarden records. The `rancher` tailnet device is removed by the operator
when its Ingress is deleted; Bitwarden records `rancher_k3s_*` are retained
deliberately (delete manually only with operator approval).

Recovery notes:

- Stuck release: `helm history rancher -n cattle-system`,
  `helm rollback rancher -n cattle-system <rev>`.
- Proxy issues: `kubectl -n tailscale logs deploy/tailscale-operator`
  (read-only) and `kubectl -n tailscale get pods`. Never restart or delete
  the operator or another service's proxy pod.
- Tailnet Lock: this tailnet has Tailnet Lock ENABLED. A newly minted
  `rancher` proxy node may report locked out until its node key is signed
  by a trusted signing device (`tailscale lock status`; this host holds a
  trusted key). Signing the specific pending node is part of bringing the
  endpoint up; record who signed what and when.
- Crash between changepassword and escrow: the new admin password is
  staged at `/run/rancher-k8s-admin-pending` on the target (mode 0600).
  Rerun the playbook — it probes the staged credential, escrows it, and
  finishes. Do not delete the file manually.
- Lost admin password with no staged file and no Bitwarden record: use the
  upstream Rancher procedure for resetting the admin password from inside
  the rancher container (see Rancher docs for the running version), then
  escrow the new value as `rancher_k3s_admin_password` and rerun.

## Idempotency contract

A rerun must report `changed=0`: the bootstrap record is listed and reused
(never regenerated), the admin record is only verified, Helm sees identical
values and does not upgrade, the Ingress apply is a no-op, and every read
or health task is `changed_when: false`. Any `changed=1` on a converged
rerun is a bug — find it with `--diff` and `grep -B8 '^changed:'`.
